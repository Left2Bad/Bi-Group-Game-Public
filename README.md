# BI Academy

Система анализа рабочих подходов сотрудника строительной компании. После регистрации сотрудник обязательно отвечает на **7 вопросов для создания аватара**. Затем тест предлагает **10 ситуаций из банка 300 готовых вопросов и 5 последовательных вопросов со свободным ответом**. ИИ выбирает только идентификаторы первых десяти вопросов по должности и ответам анкеты аватара; тексты и баллы этих вопросов хранятся в базе. Каждый из пяти открытых вопросов создаётся с учётом всех предыдущих ответов. Сотрудник получает:

- четыре показателя поведения: критическое мышление, уверенность в себе, дисциплина, вовлечённость;
- отдельную оценку профессиональных навыков по должности с цитатами из ответов, сильными сторонами и областями роста;
- персональный план развития на 30 дней: четыре разные практики со сроками, критериями успеха и повторный тест для сравнения.

Обе рубрики оцениваются **одним запросом ИИ после 15 ответов**. Аватар персонализирует подбор ситуаций, но не влияет на баллы. BuildEX и BIU указаны только как направления для дальнейшего изучения тем; подключения к этим системам нет.

Прохождения прежней методики (15 заранее подготовленных ситуаций, архетип и радар) остаются доступны в разделе «Результаты прежней методики» без пересчёта.

При регистрации выбирается роль: **сотрудник** проходит тест и получает свой профиль; **руководитель** создаёт команды, приглашает сотрудников по коду и видит их результаты, средние значения и тепловую карту. Аккаунт доступен сразу, подтверждать почту не нужно. Вход по email и паролю, права определяет сервер.

## Главные решения

**Адаптивный тест.** При старте ИИ выбирает десять ID из таблицы `question_bank`, учитывая должность, аватар и уже показанные вопросы. Сервер проверяет уникальность ID и покрытие четырёх качеств, затем сохраняет неизменяемый снимок выбранных вопросов в попытке. Пять открытых вопросов генерируются по одному после предыдущего ответа. При отказе сервиса черновик остаётся на сервере и запрос можно повторить.

При старте выполняется один вызов выбора ID. Список выбранных ID сохраняется в SQLite, поэтому повтор после сбоя использует тот же набор, в том числе после перезапуска сервиса. Если до создания снимка попытки вопросы из списка удалены из банка, десятка подбирается заново. Параллельные запросы одного этапа объединяются в рамках процесса сервера. Удаление истории очищает и промежуточный набор.

**Синхронизация банка.** При каждом запуске API содержимое `server/bank/*.json` и исходные 15 вопросов из `src/content/questions.ts` сверяются с рабочей SQLite: новые ID добавляются, изменённые вопросы обновляются, исчезнувшие получают `active = 0`. Сверка идёт по содержимому даже без изменения версии и выполняется одной транзакцией. Снимки вопросов в начатых и завершённых попытках сохраняются. См. [источники и обновление банка на сервере](docs/question-bank.md).

Диагностика AI выводится в stdout/stderr с префиксом `[assessment-ai]` (в Coolify — вкладка Logs после обновления сервиса). Записываются этап, модель/пресет, статус, ID запроса/ответа, использованные токены при полученном usage и причина отказа. Ключи, тексты вопросов и ответы сотрудников в лог не попадают. Ошибки API, тайм-аут, незавершённый ответ, неверный формат и отказ проверки качества имеют разные сообщения. Отказ локальной проверки после успешного ответа API не отменяет уже использованные токены.

**Раздельные результаты.** Четыре качества показываются в процентах. Для каждого итог складывается из выбора в десяти ситуациях (вес 2/3) и поведенческой оценки по всем 15 ответам (вес 1/3). Профессиональные навыки показываются отдельно: ИИ выделяет 3–5 навыков по должности и оценивает каждый по рубрике 0–4. Это предварительная оценка для развития, а не подтверждение квалификации.

**Объяснимость.** Для каждого процента видно, из каких ответов он сложился и почему. Рекомендация привязана к конкретному слабому ответу, а не к общему проценту.

**Аккаунты и доступ.** Новые черновики, тексты всех показанных вопросов, ответы и оценки хранятся в SQLite на сервере без автоматического удаления старых попыток; история загружается страницами. Руководитель видит результат участника только после его согласия. Для OpenAI передаются рабочая роль, ответы и ограниченная история прохождений; ключ находится только на сервере. Пароли хранятся как scrypt-хеши, сессии — в HttpOnly-cookie. Подробности: [регистрация и команды](docs/internal/auth.md).

## Запуск

Нужны Node.js 24.13.1 (см. `.nvmrc`), npm 11 и серверный `OPENAI_API_KEY`. Модель задаётся `OPENAI_MODEL` (по умолчанию `gpt-6-luna`), уровень размышлений — `OPENAI_REASONING_EFFORT` (по умолчанию `high`). Скопируйте `.env.example` в `.env` и задайте ключ. Без ключа новое прохождение не создаётся; прежние результаты остаются доступными.

```dotenv
OPENAI_API_KEY=ваш_ключ
OPENAI_MODEL=gpt-6-luna
OPENAI_REASONING_EFFORT=high
```

Для GPT-6 Luna допустимы `none`, `low`, `medium`, `high`, `xhigh`, `max`; они передаются как `reasoning.effort` в Responses API. Значение `default` убирает этот параметр из запроса — например, при выборе модели без поддержки reasoning. `none` передаётся явно и отличается от `default`. Поддержку пресета при смене модели нужно сверять с её документацией. Эти настройки серверные; после изменения `.env` перезапустите API, а для Docker пересоздайте контейнер (`docker compose up -d --force-recreate`).

Выбранные модель и пресет закрепляются за новой попыткой. Изменение окружения не меняет уже начатые прохождения; для применения новых настроек начните новую попытку после завершения текущей. В старых попытках без пресета reasoning по-прежнему не передаётся. Проценты с разными пресетами не сравниваются напрямую.

GPT-6 получает лимит 25 000 токенов на размышления и структурированный ответ вместе; старые запросы без reasoning сохраняют лимит 8000. Выбор ID, каждый открытый вопрос и итоговое оценивание имеют тайм-аут 120 секунд. Это стартовые технические лимиты, а не измеренная длительность.

```sh
npm ci
npm run dev:api    # API: http://localhost:3001 (отдельный терминал)
npm run dev        # интерфейс: http://localhost:5173, /api проксируется на 3001
npm run build && npm start   # production: http://localhost:3000, health — /healthz
```

Docker: `docker compose up --build --wait`. База сохраняется в томе `academy-data` (`/app/data`). Для Coolify обязательно добавить persistent storage на `/app/data` и `COOKIE_SECURE=true` при HTTPS. За reverse proxy рекомендуется задать `PUBLIC_ORIGIN=https://ваш-домен` без пути, особенно для браузеров без Fetch Metadata; это предотвращает ошибку «Источник запроса не разрешён.» при замене Host прокси-сервером. См. [регистрацию и хранение](docs/internal/auth.md) и [Coolify](docs/internal/coolify.md).

Тестовые аккаунты для проверки (руководитель, шесть сотрудников его команды с результатами и новичок без данных, пароль `test123456`) создаются или пересоздаются кнопкой «Сбросить тестовые аккаунты» внизу кабинета любого руководителя (`/team`) или одной командой: локально `npm run seed:test-accounts`, в контейнере `docker compose exec academy node server/seed-test-accounts.mjs`, в Coolify — та же `node server/seed-test-accounts.mjs` в терминале приложения. Повторный запуск стирает всё содержимое этих аккаунтов (сессии, попытки, аватары, команду, отметки, комментарии, беседы) и записывает заново; другие пользователи не затрагиваются. Данные берутся из `server/test-accounts.json` — это вымышленная команда примера, посчитанная той же методикой, модель не вызывается. После правок примера фикстуру пересобирает `npm run test-accounts:build`, а тест напоминает об этом.

## Проверки

Перед первым браузерным запуском установите браузеры: `npx playwright install chromium firefox`. Если порт 3000 занят, задайте `E2E_PORT` со свободным портом; новый динамический набор по умолчанию использует 3101.

```sh
npm run check      # lint, unit/component-тесты, типы, сборка
npm run test:e2e   # браузерные сценарии: Chromium desktop/mobile и Firefox
npm run test:e2e:dynamic # production-маршруты 10 + 5, черновик и отказ API
```

Тесты новой методики проверяют формат 10 + 5, выбор ID из банка, отдельные рубрики, ограничение опасных решений, точность цитат, восстановление после отказа API, параллельный старт, отмену после удаления и права доступа. Запросы к OpenAI в тестах подменяются контролируемыми ответами; реальную работу модели нужно дополнительно проверить с серверным ключом. Отдельный браузерный запуск использует production-сборку. Основной браузерный набор сохраняет регрессионные проверки прежней методики в специальной сборке `playwright-legacy`.

Формат Responses API и Structured Outputs сверены с [официальной документацией OpenAI](https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=responses). При смене модели проверяйте поддержку строгого JSON Schema.

## Языки интерфейса

RU, ҚАЗ и EN. Ключ перевода — русская строка из `t()`/`msg()`; словари: `src/i18n/kk.ts`, `en.ts` (интерфейс) и `en-content.ts` (содержимое). Язык по умолчанию — первый поддерживаемый из языков браузера, сохранённый выбор важнее. Тексты самого теста (`src/content/questions.ts`, `server/bank/*.json`, вопросы ИИ) не переводятся и в словари не попадают. Строки, ожидающие казахского перевода, перечислены в `src/i18n/kk-pending.ts`; тест `i18n.test.ts` сверяет список в обе стороны. Для Playwright задан `locale: 'ru-RU'`, чтобы тесты шли на русском.
