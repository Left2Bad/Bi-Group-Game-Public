## 002. Общий контракт (D1-03)

Единый источник типов — `src/domain/types.ts`. Только этот файл и синтетический fixture созданы A в области C по прямому заданию D1-03. Дальше C владеет реализацией domain/content/эталонов. Изменения общих типов фиксируются в handoff для следующего участника; фактическая совместимость проверяется при интеграции.

- Порядок `TRAIT_IDS`: criticalThinking, confidence, discipline, engagement. Четыре независимые шкалы, без среднего «процента личности».
- `Question.options` — readonly tuple из четырёх вариантов; ID вопросов Q01…Q15, ID варианта уникален внутри вопроса (fixture использует Q01-A и т. п.). `Answers` — словарь ID вопроса → ID варианта; пропуски представляются отсутствующим ключом.
- `DataVersions`: отдельно schema (число), assessment, scoring, recommendations (строки). Изменение содержания/правил/рекомендаций требует изменения соответствующей версии. Изменения текстов вопросов тоже меняют assessment.
- `AssessmentResult`: attemptId, completedAt (ISO UTC), versions, копия answers и record всех четырёх `TraitResult`. Свидетельство включает вопрос, выбранный вариант, баллы, причину, тег и качество. Время/ID передаются извне для детерминизма; входные объекты не мутируются.
- `TraitResult.percent` — округлённое число для экрана. Уровень и сортировка используют points/maxPoints до округления: priority < 50%, developing < 75%, strength >= 75%. Ничьи — порядок TRAIT_IDS.
- `DevelopmentPlan` содержит до двух priorityTraits и карточки Recommendation. Каждая карточка имеет причину, действие, практику, срок в днях, критерий и связанные вопросы. Полностью высокие результаты получают поддерживающие действия без выдуманных слабостей. Логику и содержание реализует C.
- `Draft` содержит versions, answers, currentQuestionId, updatedAt. Демо и реальный черновик должны быть раздельны.

Публичные функции C (тип функции экспортирован отдельно для проверки совместимости):

```ts
// src/domain/validate.ts
export const validateAnswers: ValidateAnswers = (answers, questions) => /* ... */
// src/domain/score.ts
export const calculateProfile: CalculateProfile = (answers, context) => /* ... */
// src/domain/recommend.ts
export const buildRecommendations: BuildRecommendations = (result) => /* ... */
```

`answers: unknown` позволяет отвергать испорченный JSON и неизвестные варианты. `validateAnswers` проверяет полный набор и возвращает discriminated union с `ok` и issues. Черновик проверяется отдельно и может быть неполным. `calculateProfile` получает `CalculationContext` с вопросами, scoring, версиями, временем и attemptId; возвращает `{ok:true,result}` или `{ok:false,error}`. Неполный/неизвестный ответ — ошибка, профиль не публикуется; некорректный набор контента — `invalid-content`.

`buildRecommendations(result)` использует таблицы рекомендаций C для версии result. Проверка версий до вызова — обязанность точки интеграции A; результат другой версии не пересчитывается по новым правилам молча. Повторный расчёт не изменяет старую попытку. `loadDraft(): LoadDraftResult` и `saveDraft(draft): SaveDraftResult` реализует A в D2-03; статусы отдельно различают пустое, повреждённое, несовместимое и недоступное хранилище. Реализаций этих пяти функций в первом блоке нет.

## 007. Безопасный черновик (D2-03)

`createDraftStorage({questions, versions, getStorage?})` в `src/storage/draft.ts` возвращает функции `loadDraft()` и `saveDraft(draft)` с общими сигнатурами. Фабрика позволяет связать хранилище с реальным каталогом C без глобальной конфигурации и подменить storage в проверках. Модуль не начисляет баллы.

Загрузка различает empty/loaded/invalid/incompatible/unavailable; проверяет все четыре версии, ISO timestamp, текущий вопрос и частичные ответы только на известные варианты. Ограничение JSON — 64 KiB. Повреждённый/старый черновик не удаляется автоматически; решение о сбросе принимает пользователь. Запись хранит снимок и не перезаписывает старые данные при невалидном входе. Получение localStorage, getItem, setItem и removeItem могут отказать — ошибки возвращаются как статус.

Собственные ключи `bi-academy:draft`, `bi-academy:attempts`, `bi-academy:actions` объявлены в shared.ts. `clearAppData` удаляет только их; localStorage.clear не используется. Статусы подключены к состоянию/UI и работе в памяти в следующем блоке; восстановление Q07 проверено через новый экземпляр сессии и remount React с jsdom localStorage.

## 009. История и редактирование (D3-04/D3-05)

`createAttemptStorage` хранит до 10 immutable snapshots под отдельной схемой истории. Одинаковый submit идемпотентен, иной результат под тем же attemptId отвергается; при коллизии ID сессия не публикует замену старого результата. Повреждённая/неизвестная схема не перезаписывается автоматически. Проверка сериализованной формы — в storage; формулу по-прежнему реализует C.

При reload сессия пропускает результат текущей версии через calculateProfile с исходными metadata/answers и сравнивает весь снимок. Подменённые цифры/причины не показываются. Иная версия сохраняется в истории, но открытие/редактирование и сравнение с ней блокируются. `compareAttempts` возвращает четыре изменения отображаемых процентов в п.п.; один attempt не сравнивается сам с собой.

После успешного сохранения истории черновик удаляется. Если запись истории отказала, результат остаётся в памяти и полный черновик сохраняется для восстановления. `openAttempt` не меняет активный черновик. `editCompletedAttempt` создаёт копию ответов с новым ID при завершении; исходная история не переписывается. Контролы повторения/редактирования — в оболочке A, визуальный профиль/график сравнения остаются B.

## 011. Отметки действий для маршрута B

`createActionStorage({attemptId, versions, recommendationIds})` в `src/storage/actions.ts` хранит отметки отдельно от результатов. `loadActions()` возвращает completedIds/статус; `setCompleted(id, boolean)` ставит/снимает отметку и возвращает статус записи. Учитываются все версии, разрешённые ID и отдельная попытка; чужие/старые отметки не приклеиваются к новому результату. Максимум 10 попыток, 32 отметки на попытку. Ошибки/неизвестная схема не перезаписывают данные автоматически.

Vitest ограничен maxWorkers=2: после роста набора до 10 файлов Windows исчерпал доступную память при стандартном числе workers. После завершения временного QA-preview и ограничения параллелизма все 105 тестов, lint, типы и build прошли. Изоляция тестовых файлов сохранена.

## 017. Продолжение экранов B и отметки маршрута

17.10 владелец прямо разрешил этому чату A доделать оставшиеся экраны B. Разрешение распространяется на UI B и интеграцию A; формула, тексты вопросов и методика C не меняются. Сохраняем принятую зелёную тему B, не начинаем отдельное приложение.

DevelopmentPage принимает plan/completedIds/onCompletedChange/notice/warning, storage вынесен в development-session A. Основной маршрут представляет до двух priorityTraits C; при их отсутствии — до двух maintenance практик. Полный план C остаётся в печатном отчёте, поэтому остальные низкие качества также имеют доступную рекомендацию. Подписи практик/сроков/критериев берутся из C; учебные программы не выдумываются.

Отметки читаются/пишутся createActionStorage, ключи draft/history и результат не меняются. Кэш контроллеров до HISTORY_LIMIT хранится по attemptId и всем версиям, очищается удалением личных данных. При отказе storage контроллер до конца сессии остаётся memory-only, чтобы следующая успешная запись не потеряла предыдущие несохранённые отметки; переходы SPA их сохраняют. Повреждённый/несовместимый JSON не перезаписывается. Достоверность профиля не зависит от выполнения практик.

## 018. Объяснимый профиль и доступность экранов B

ResultsPage получает result/questions/plan, показывает готовые уровни C и все 15 evidence: ситуацию, выбранный вариант, баллы, reason. Уровни/приоритеты в UI не пересчитываются. При отсутствии strength наибольшие показатели внутри профиля подписываются относительными опорами (все ничьи максимума сохраняются); при равенстве всех четырёх не выделяется произвольная опора. По max показывается поддержание. Короткий тест не подаётся как профессиональная диагностика или доказательство роста.

Вводная использует общий ActionLink; базовый цвет ссылок задан малоспецифичным a, поэтому белые/декоративные ссылки B не переопределяются. Focus потемнел до #b55f00 и получил белую подложку для тёмной поверхности. Обещание длительности убрано до человеческого замера.

В штатный Playwright добавлен Firefox и полностью клавиатурный сценарий без click/check/focus: Tab/Arrow/Space/Enter через весь тест, review, четыре details и два checkbox. В CI устанавливаются оба браузера. Native zoom 200% проверен отдельно через штатные настройки собственного persistent Chromium (полный channel chromium); Playwright headless-shell не содержит Settings. Это не изменение пользовательского браузера. При native zoom координаты element screenshots некорректны, для осмотра использованы CDP viewport screenshots после двух кадров. Реальный телефон/Safari не тестировались.

## 019. Изолированное демо и завершение технической части C

17.10 владелец разрешил этому чату продолжить C после B. Содержание, формула, DATA_VERSIONS и рекомендации bi-academy-v1 сохранены. Runtime не импортирует tests/fixtures; methodology.test сравнивает production-fixture с независимым ручным эталоном.

DemoPage вызывает общий calculateProfile/buildRecommendations напрямую; выбранный набор и отметки A/B — локальный React state, без assessment/development контроллеров, storage и записи в историю. ## 020. Материалы защиты и воспроизводимый комплект

После сброса лимитов владелец уточнил предварительный формат: репозиторий, презентация и сайт; Coolify подключается позже. Чистый clone 062d51e с готовыми B/C проверен заново на Windows и Linux. Приложение/методика остаются на runtime-коде abfb829, новые команды не меняют результат теста.

capture:review поднимает production app на свободном loopback-порту, выполняет реальное прохождение вымышленным примером и A/B в свежем контексте, сохраняет снимки/видео с source commit, закрывает свои ресурсы. Сайт, репозиторий без входа, человеческое прохождение, репетиции и отправка проверяются отдельно. Repository API без авторизации возвращает 404; видимость не меняется автоматически.

## 022. Примеры по действующей методике

20.10 владелец попросил привести примеры к актуальному виду экранов сотрудника и руководителя. /demo и /team/demo в рабочей сборке показывают те же компоненты, что и настоящие кабинеты: DynamicProfile, маршрут DevelopmentRoute, экран команды сотрудника, лист команды TeamSheet и карточку ManagerEmployeeCard. Для этого маршрут и лист команды вынесены из страниц, которые загружают данные с сервера, без изменения их поведения.

Данные — вымышленная команда участка из src/content/dynamic-demo.ts: 10 ситуаций дословно из банка (по 5 на качество), 5 открытых вопросов, ответы и уровни рубрики, составленные вручную. Отметки, комментарии и беседы живут в памяти страницы; сервер и хранилище не используются, код пропуска не проходит проверку формата.
