# Регистрация, роли и команды

Обновление от 18.10.2026: регистрация изначально реализована поверх `839b6b4`, затем объединена с дизайн-коммитами `d27e66e` и `b77f5ae`. Регистрация и вход работают через Express API; прежний экран вымышленной команды сохранён на `/team/demo`.

## Как проверить вручную

1. Открыть `/register?role=manager`, выбрать «Руководитель», указать имя, email и пароль от 10 символов. После регистрации откроется `/team`.
2. Создать команду и скопировать её код. Руководитель может создать несколько команд и переключаться между ними.
3. В другом браузере/приватном окне зарегистрировать сотрудника на `/register`. Код можно указать сразу или позже на `/account`.
4. Сотрудник проходит 10 ситуаций с четырьмя вариантами и 5 открытых вопросов. Новые вопросы и каждый ответ сохраняются на сервере; при ошибке OpenAI API можно повторить запрос без потери черновика.
5. Руководитель нажимает «Обновить результаты»: видит участников, статус прохождения, последний профиль сотрудника, командную аналитику и экспорт JSON/CSV.
6. Войти в аккаунт сотрудника на другом устройстве: полный список новых попыток доступен постранично, активный черновик и отметки нового маршрута восстанавливаются с сервера. Аватар и отметки прежней методики остаются на исходном устройстве.
7. Сотрудник может выйти из команды, руководитель — убрать участника. После этого API руководителя больше не возвращает его данные. Личный результат сотрудника сохраняется.

Руководитель не проходит личный тест из своего кабинета. Сотрудник может пройти тест без команды. Один email соответствует одному аккаунту с выбранной при регистрации ролью; переключения роли и просмотра списка чужих пользователей нет.

По решению владельца подтверждение почты не требуется: после регистрации аккаунт сразу доступен и пользователь автоматически входит. Для последующего входа нужны только email и пароль. Имя и роль задаются при регистрации для профиля и разделения доступа. Письма, ссылки и коды подтверждения не отправляются; почтовый сервис для регистрации не нужен. Восстановление пароля не реализовано. Код приглашения в команду передаёт сам руководитель.

## Хранение и запуск

Node **24.13.1** выполняет серверные `.ts` без отдельной сборки; используется встроенный `node:sqlite`. Сервер и клиент импортируют один вычислитель `src/domain/score.ts` и один каталог вопросов. Клиент отправляет ответы и версии, сервер заново вычисляет проценты. Переданные клиентом проценты не используются.

По умолчанию база — `data/academy.sqlite`, путь можно изменить переменной `DATABASE_PATH`. Каталог создаётся при запуске, база и её WAL-файлы исключены из Git и Docker build context. При локальной разработке нужны два терминала: `npm run dev:api` и `npm run dev`. Vite проксирует `/api` на порт 3001. После `npm run build` команда `npm start` обслуживает API и интерфейс на 3000.

Compose использует том `academy-data:/app/data`, основной filesystem остаётся read-only. В Coolify для Dockerfile-приложения вручную подключить постоянное хранилище к `/app/data`, задать `DATABASE_PATH=/app/data/academy.sqlite` и `COOKIE_SECURE=true` при HTTPS. Каталог должен быть доступен пользователю `node` (UID 1000). Пересоздание контейнера без этого тома потеряет аккаунты. Для резервного копирования остановить приложение и скопировать весь каталог базы; один Docker image данные пользователей не содержит.

Если прокси заменяет публичный `Host` внутренним адресом контейнера, прежнее сравнение `Origin.host` с `Host` возвращало «Источник запроса не разрешён.» ещё до проверки полей и роли. Локальный случай `http://localhost:5173/register` также воспроизведён: строковая настройка proxy в Vite 8 включает `changeOrigin: true` и заменяет Host на `127.0.0.1:3001`. В `vite.config.ts` явно задано `changeOrigin: false`, чтобы сохранить исходный Host; для локальной разработки `PUBLIC_ORIGIN` не нужен.

Серверная проверка исправлена для всех операций записи, включая регистрацию, вход, выход и команды. Браузерные запросы с `Sec-Fetch-Site: same-origin` разрешены при корректном HTTP(S) Origin; `cross-site`, `same-site`, `none` и неизвестные значения отклоняются. Заголовки `Sec-*` устанавливает браузер, клиентский JavaScript не может их подделать. Обязательный `X-BI-Academy` и запрет CORS для чужих сайтов сохранены.

Для production рекомендуется явно задать `PUBLIC_ORIGIN=https://ваш-домен` (схема, домен и при необходимости порт, без пути). Это также обеспечивает работу через прокси при отсутствии Fetch Metadata, например при открытии публичного сайта по HTTP. При заданной переменной любой переданный Origin должен точно совпадать с ней, включая схему и порт. Некорректная настройка останавливает запуск. Для HTTPS дополнительно нужен `COOKIE_SECURE=true`; compose передаёт обе переменные из окружения. Без `PUBLIC_ORIGIN` и Fetch Metadata выполняется точное сравнение Origin со схемой и Host прямого запроса. Значения `X-Forwarded-Host`/`X-Forwarded-Proto` автоматически не считаются доверенными. После изменения кода нужно пересобрать и перезапустить развёрнутое приложение.

Подход соответствует [рекомендациям OWASP по Fetch Metadata и определению внешнего Origin за прокси](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html#use-fetch-metadata-headers-to-verify-nature-of-the-request).

## Права и сессии

Пароли: scrypt со случайной солью. Cookie сессии: HttpOnly, SameSite=Lax, семь дней; на HTTPS с `COOKIE_SECURE=true` также Secure. В базе хранится хеш токена. Выход отзывает текущую сессию; роль берётся из базы на каждом запросе. Запросы записи требуют собственного заголовка и проверки Origin; регистрация/вход/подбор приглашений ограничены по IP.

Коды команд случайные, 16 шестнадцатеричных символов. Только владелец команды видит её участников и результаты. Сотрудник видит свои попытки и название своей команды, не чужие результаты. Вступление открывает руководителю завершённые ответы и результаты; это объяснено в регистрации и кабинете. Выход из команды прекращает серверный доступ, но не отзывает уже скачанный руководителем экспорт.

Локальные ключи теста содержат ID аккаунта. Выход/смена аккаунта пересоздают контроллеры; случайного переноса старых анонимных результатов в новый аккаунт нет. Заголовок с ID известного клиенту пользователя предотвращает запись в другой аккаунт при смене cookie в соседней вкладке. При возвращении фокуса сессия перепроверяется.

«Удалить мои данные» удаляет серверные попытки и данные теста на этом устройстве, оставляя аккаунт и членство в команде. Отправка и удаление выполняются последовательно. При ошибке удаления сервера локальные результаты сохраняются, чтобы пользователь мог повторить операцию.

На форме входа флажок «Начать заново при входе» после проверки пароля сбрасывает прогресс аккаунта. У сотрудника удаляются попытки старого и нового теста, черновик генерации, отметки практик, аватар и членство в команде. Данные этого аккаунта в текущем браузере очищаются сразу, а в других браузерах — при следующем входе, по сохранённой на сервере отметке сброса. После входа сотрудник снова проходит создание аватара. У руководителя удаляются созданные команды (сотрудники сохраняют свои аккаунты и результаты, но выходят из этих команд). Прежние сессии аккаунта отзываются. Без флажка обычный вход сохраняет прогресс.

Сотрудник может зарегистрироваться без кода и вступить позже: на вводном экране есть ссылка «Ввести код команды», а в кабинете сотрудника — поле кода и согласие на передачу результатов руководителю.

## Валидация форм и API

Общие правила находятся в `src/domain/account-validation.ts`; формы и сервер используют один модуль. Обход HTML-ограничений не обходит серверные проверки:

- Имя: после удаления пробелов по краям 2–80 символов, есть буквы, нет управляющих знаков. Национальные имена, апострофы и дефисы разрешены.
- Email: пробелы по краям удаляются, регистр приводится к нижнему; проверяются структура адреса, точки, длина локальной части/доменов и общий предел 254 символа. Поддерживается обычный ASCII-адрес, совместимый с полем `type=email`; существование почтового ящика не проверяется.
- Новый пароль: 10–128 символов, не только пробелы. Значимые пробелы сохраняются при регистрации и входе. Состав из цифр/спецзнаков искусственно не ограничивается. При входе проверяется непустой пароль до 128 символов, чтобы не менять требования к ранее созданным аккаунтам.
- Роль при регистрации: только `employee` или `manager`. Поле роли в запросе входа игнорируется: роль берётся из базы.
- Код команды: строка из 16 шестнадцатеричных символов, регистр и пробелы по краям нормализуются. При регистрации сотрудника необязателен; при вступлении обязателен. Неверный тип не игнорируется. Несуществующее приглашение не создаёт аккаунт частично.
- Название команды: 2–80 символов после удаления пробелов по краям, без управляющих знаков.

Ошибки API могут содержать `fields`; форма связывает их с полями через `setCustomValidity`, фокус браузера и `aria-invalid`, а текст показывает в существующем блоке ошибок. Нативный всплывающий `reportValidity` не используется: в Firefox его старая подсказка могла перекрывать кнопку даже после исправления поля. Исправление значения снимает ошибку; после отказа API кнопка снова доступна. Запросы ограничены 15 секундами, повторная отправка регистрации во время запроса блокируется. Стили и оформление не менялись.

Выход проверяет ID аккаунта, известный вкладке: устаревшая вкладка не отзывает сессию другого аккаунта. Повторная отправка сохранённой попытки также проходит проверку ответов и даты; другой набор ответов с тем же ID возвращает 409 и не перезаписывает результат.

## Согласие и карточка развития сотрудника

**Согласие.** Вступить в команду (при регистрации по коду или в кабинете) можно только с отмеченным флажком «Согласен(на) передать руководителю команды мои результаты теста, их динамику и мой аватар». Сервер принимает только `consent: true` и сохраняет в `memberships` дату (`consented_at`) и версию текста (`consent_version`, сейчас 1). Без согласия `GET /api/teams/:id` не отдаёт результат, историю и аватар участника, а у руководителя он помечен «Ожидает согласия сотрудника». Участники, вступившие до появления согласия (после миграции у них `consented_at = NULL`), подтверждают его в кабинете: `PUT /api/membership/consent`. Отзыв согласия — выход из команды; руководитель сразу теряет доступ. Миграция существующей базы выполняется автоматически при старте (`ALTER TABLE … ADD COLUMN`).

**Аватар.** Созданный сотрудником аватар синхронизируется с сервером (`GET/PUT /api/avatar`, таблица `avatars`). Сервер сохраняет только допустимые значения из конструктора; `avatar: null` возвращает персонажа по тесту. На новом устройстве аватар восстанавливается с сервера.

**Карточка развития сотрудника** (кабинет руководителя → «Результат …») загружается отдельным запросом `GET /api/teams/:id/members/:userId/card`. Сервер отдаёт её только руководителю этой команды и только при действующем согласии сотрудника: для чужой команды или человека не из команды ответ 404, без согласия 403. В ответ входят последняя завершённая попытка, история оценок для сравнения (без вопросов и ответов прежних попыток), отметки практик текущего маршрута и аватар. Карточка показывает четыре качества и профессиональные навыки раздельно, без общего процента. Навыки сравниваются по устойчивому `skillId` и версии каталога `professional-skills-v1` (`src/dynamic/skills.ts`); расчёт карточки — чистые функции `src/dynamic/manager-card.ts`. Входной считается первая попытка, сопоставимая с последней по существующим правилам `comparableDynamic`. Результаты без `skillId` показываются как есть, без динамики. Навыки, ожидаемые от должности, но не оценённые, помечены «Недостаточно данных». Отметки практик — «Отмечено сотрудником», а не подтверждение руководителя. BuildEX, BIU и KPI показаны как неподключённые внешние этапы. Если сотрудник проходил только прежнюю методику, карточка показывает её четыре качества без пересчёта, а полный старый профиль раскрывается отдельно. Разница попыток не доказывает рост навыка.

**Беседы руководителя с сотрудником.** В профиле команды, подраздел «Качества сотрудников», у сотрудника с показателем ниже 55% (новая методика) или в зоне «приоритет» (прежняя) появляется кнопка «Назначить беседу»: дата, время и необязательное сообщение. Сервер сам проверяет команду, согласие, будущую дату и наличие показателя ниже нормы (таблица `meetings`, `server/meetings.ts`). Сотрудник принимает или отклоняет приглашение в колокольчике уведомлений в шапке; руководитель видит там, кто ответил, и список встреч, и может отменить будущую встречу. Одному сотруднику можно отправить не более 5 неотвеченных приглашений. Комментарии к маршруту и беседы не меняют оценки.
